# 霍旌【协攻】：强制空响应崩溃边界

## 结论摘要

1. `hasUsableCard("sha", "respond") === true` 只表示一个粗粒度的“可能有可用杀”。它会检查 `hs` 中的实体牌，也会把响应型 `viewAs`/`hiddenCard` 技能计入；而且调用时取得的事件可能仍是 `useCard1` 技能事件，不一定是随后真正建立的 `chooseToRespond`。因此它不保证下一步选择事件一定存在可选实体牌。
2. `forced: true` 的空选择路径是源码确定的：选择事件默认要选 1 张；`game.Check.processSelection` 在 `forced` 且没有任何可选项时放宽“至少选一张”的失败条件，`game.check()` 返回真；随后 `ui.click.ok()` 以空的 `cards[0]` 生成无牌名的自动视牌对象。`player.respond` 不会把这个无牌名对象当作响应牌，最终 `respond` 事件的 `event.card` 仍为 `undefined`；`content.js` 随后读取 `event.card.name`，因而崩溃。
3. 当前触发过滤只看帅使用事件的 `event.card.name === "sha"`，不看 `isCard` 或实体组成牌。帅使用实体【杀】和虚拟/转化【杀】都会触发【协攻】；这两者只影响牌的实体去向和表示，不改变该触发条件。
4. “只有实体且 `cardRespondable` 的【杀】才 `forced`；虚拟/误报分支非 forced；失败则交牌”是已知崩溃的正确最小方向，现有 smoke test 也覆盖了虚拟误报分支。但它仍有预检后牌被移除、`onChooseToRespond` 或第三方钩子改变合法性的残余窗口。最稳妥的补强是：无论 `forced` 取值，`forResult()` 后必须验证 `result.bool === true`、存在实体 `result.cards[0]`、牌名为 `sha` 且仍通过 `cardRespondable`/事件过滤；否则绝不调用 `player.respond`，直接进入交牌失败分支。

## 1. 为什么预检可能真而强制选择仍无牌

### 1.1 `hasUsableCard` 的真值来源不止实体牌

`noname/library/element/player.js:2844-2869` 的实体牌分支会在 `hs` 中按 `get.name(i, player) === name2` 筛牌；`type === "respond"` 时调用 `lib.filter.cardRespondable(i, player, evt)`。但继续向下的 `:2886-2943` 还遍历隐形技能：

- `:2905-2925`：`info.viewAs` 是对象且名称为 `sha` 时，只要 `viewAsFilter`、技能 `filter`/`enable` 和当前事件过滤通过，就返回真；这可能没有任何实体杀。
- `:2926-2943`：`hiddenCard(player, "sha")` 返回真且技能事件过滤通过，也返回真；同样可能没有可供 `chooseToRespond` 选取的实体牌。

另外，`noname/library/element/player.js:613-618` 的 `canRespond` 文档直接注明只能“粗略判断”，有些情况无法判断。`hasUsableCard` 本身没有为即将创建的选择事件预留牌，也没有把最终选择结果锁定。

### 1.2 预检和实际选择的 `cardRespondable` 上下文可能不同

`noname/library/index.js:10973-11002`：`cardRespondable` 在传入事件名称不是 `chooseToRespond` 时直接返回真（`:10974-10977`）；只有 `event.name === "chooseToRespond"` 才检查来源的 `norespond` 标签（`:10984-10989`）、实体牌的 `cardEnabled2`（`:10990-10995`）和 `cardRespondable` mod（`:10996-11001`）。

`hasUsableCard` 在 `:2849-2864` 通过当前事件及其父事件寻找 `chooseToRespond`，找不到时退回当前事件。因此从 `useCard1` 技能内容调用时，存在“预检传入 `useCard1`，`cardRespondable` 因事件名直接放行”的过宽路径。

随后真正的选择由 `noname/game/check.js:106-121` 执行：它调用 `lib.filter.cardRespondable(card, player)`（未显式传 event，因而依赖当前 `_status.event`），再调用 `event2.filterCard(card, player)`。此时 `_status.event` 已是 `chooseToRespond`，且可能受到上述 `norespond`、mod 和动态钩子的影响。故即使预检为真，实际可选集合仍可为空。

### 1.3 预检与选择之间还有状态窗口

当前重写模块 `nihilphile武将包/module/huojing_rewrite.js:248-268` 先调用 `hasUsableCard`，再创建选择事件并 `await choose.forResult()`。源码没有在两者之间锁定实体牌；选择事件的 `onChooseToRespond` 钩子也会在 `noname/library/element/content.js:4788-4795` 运行。由此可推断，牌被移动、技能被禁用或过滤器改变后，预检真值仍可能与最终选择集合不一致。此项是时序/第三方动态风险，不是本次静态范围内已实机复现的独立案例。

## 2. `forced:true` 空选择的确切路径

路径如下：

```text
nihil_xiegong.content
  -> hasUsableCard("sha", "respond") == true
  -> player.chooseToRespond("...", {name:"sha"})
  -> choose.set("forced", true)
  -> choose.forResult()
  -> chooseToRespond content: game.check()
  -> 无可选牌，但 forced 放宽最少选择数 -> ok == true
  -> ui.click.ok()
  -> result = { bool:true, cards:[], card:nameless VCard }
  -> player.respond([], undefined, ...)
  -> respond content 读取 event.card.name -> TypeError
```

逐点证据：

1. `noname/library/element/player.js:5418-5498` 创建 `chooseToRespond`；默认 `selectCard` 是 `[1,1]`（`:5459-5464`），牌区最终是 `hs`（`:5493`）。
2. `noname/game/index.js:6853-6891` 的 `game.check` 依次执行 card/target 检查；`:6938-6958` 汇总 `ok`。`noname/game/check.js:82-86` 的关键条件是：当选中数小于最少数时，只有 `!event.forced || selectableItems || event.complexSelect` 才把 `ok` 置为假。无可选项时 `selectableItems === false`；`forced === true` 反而使该条件为假，空选择保持 `ok === true`。
3. `noname/library/element/content.js:4837-4882`：AI 响应阶段先 `ok = game.check()`（`:4842-4844`）；既然为真，直接 `ui.click.ok()`，不会走取消。
4. `noname/ui/click/index.js:2975-3045` 的 `ok` 生成 `bool:true`、选中卡数组（空数组）及目标；对 `chooseToUse/chooseToRespond` 在 `:3027-3029` 执行 `result.card = get.autoViewAs(result.cards[0])`，空数组的第一个元素是 `undefined`。在本版本 `get.autoViewAs` 会构造一个没有 `name` 的 `VCard`（`noname/get/index.js:1049-1054`、`noname/library/element/vcard.js:44-107`），不是一张可响应牌。
5. `noname/library/element/content.js:5003-5047`：`event.result.bool` 为真且无 skill 时，在 `:5032` 调用 `player.respond(event.result.cards, event.result.card, ...)`。
6. `noname/library/element/player.js:7680-7717`：`respond` 从空 cards 保持 `next.cards=[]`；无牌名的 VCard 不满足其对象牌参数分支（`:7694-7695`），故 `next.card` 仍未定义；`:7764-7768` 进入 `respond` 内容。
7. `noname/library/element/content.js:10195-10213` 的 `respond` 内容在没有 `event.skill` 且非 `nopopup` 时，于 `:10211` 执行 `player.tryCardAnimate(event.card, event.card.name, "wood")`；即使该处被配置绕过，`:10237-10241` 的日志分支还会读取 `event.card.name`。因此截图中的 `event.card.name` 崩溃与空选择完全吻合。

相对地，`forced:false` 且没有可选牌时，`game.check()` 为假，`noname/library/element/content.js:4845-4881` 不满足 `ai.basic.chooseCard(...) || forced`，走 `ui.click.cancel()`；`noname/ui/click/index.js:3071-3091` 生成 `{ confirm:"cancel", bool:false }`。当前重写模块 `:268-280` 再把 `result.bool` 归为失败并调用 `resolveXiegongFailure`，因此“非强制失败后交牌”链条成立。

## 3. 帅使用实体/虚拟【杀】是否影响触发

不影响当前【协攻】触发。`nihilphile武将包/module/huojing_rewrite.js:238-247` 的过滤器只要求：角色在场、`event.card` 存在、`event.card.name === "sha"`、使用者是帅；没有 `event.card.isCard`、`event.cards.length` 或原始牌面检查。

引擎在 `noname/library/element/content.js:9345-9351` 从使用牌流程触发 `useCard1`。使用牌初始化时，`noname/library/element/player.js:7172-7177` 对有 card 的输入调用 `get.autoViewAs`；`noname/get/index.js:1049-1054` 将其包装成 `VCard`。`noname/library/element/vcard.js:19-37` 表明由实体 Card 包装时可带 `isCard=true` 和 `cards=[实体牌]`，而对象/技能视为的路径 `:44-70` 不必有 `isCard`，但仍保留 `name` 和默认 `cards=[]`。所以实体杀、单牌转化杀、无实体虚拟杀都能满足该触发过滤。

这不意味着下游牌移动相同：使用牌内容只对 `event.cards` 做实体失去/排序（`noname/library/element/content.js:9236-9275`），虚拟杀可能没有待处理实体牌。但这发生在触发后的牌处理层，不改变 `useCard1` 的【协攻】触发条件。

## 4. 对当前最小修复的评价

当前实现的关键辅助函数是 `nihilphile武将包/module/huojing_rewrite.js:85-94`：`hasPhysicalRespondableSha` 遍历 `hs`，要求 `get.name(card, player) === "sha"`，用即将创建的 `responseEvent` 调用 `lib.filter.cardRespondable`，再调用 `responseEvent.filterCard`。`nihil_xiegong.content` 的门和分支在 `:248-280`，设置 forced 在 `:264`。

### 正确性

- **能切断已知崩溃来源：高置信度。** 虚拟/hiddenCard 预检真但没有实体牌时，辅助函数为假，选择事件是非强制；空选择会走 cancel，随后进入交牌失败分支。
- **实体合法杀仍保持规则语义：中高置信度。** 有实体且同时通过实际响应事件的 `cardRespondable` 和 `filterCard` 时 forced 为真，多张合法牌仍由角色选一张，但不能主动取消。
- **帅的虚拟杀触发语义未被误改：高置信度。** 修复只约束协攻者的响应牌是否实体，不会错误阻止帅使用虚拟杀触发【协攻】。

### 风险

- **预检后空洞仍可能发生。** 实体牌可能在 `hasPhysicalRespondableSha` 返回后、`forResult()` 期间被移动或失效；若此时 `forced` 仍为真，仍会复现“空选择 -> `card:undefined`”路径。
- **仅用 `result.bool` 判断成功不够。** 当前 `:269` 的 `success = !!(result && result.bool)` 会把引擎的强制空确认误判为成功，然后 `:277-282` 累加协攻加成；实际应把“有实体响应牌”作为成功必要条件。
- **虚拟响应能力会被保守地降级为失败。** 这是本方案边界：一个确实能以技能视为【杀】响应、但不需要实体牌的合法能力，会被非强制选择并在未选中时交牌。若规则明确要求“实体【杀】”，这是有意取舍；若规则允许虚拟杀，则需要为该技能明确建立带 skill/viewAs 的响应事件，不能仅把 `forced` 改回真。
- **全局第三方修改仍未实机覆盖。** `onChooseToRespond`、临时禁牌、来源 `norespond` 和联机结果同步可能改变候选集合；本报告未运行 Electron/联机局。

## 5. 更稳妥的最小建议

保留当前“实体可响应才 forced、虚拟/误报非 forced”的方向，并把成功判定改为“结果后再次验证”，概念上如下（仅建议，未修改实现）：

```js
const result = await choose.forResult();
const selected = result?.cards?.[0];
const valid = result?.bool === true
  && selected
  && get.itemtype(selected) === "card"
  && get.name(selected, player) === "sha"
  && lib.filter.cardRespondable(selected, player, choose)
  && (!choose.filterCard || choose.filterCard(selected, player, choose))
  && result.card;

if (!valid) {
  // 不调用 player.respond，不累加伤害/闪数；直接进入失败交牌分支。
  await resolveXiegongFailure(player, trigger.player);
  return;
}
```

这里的 `result.card` 检查是为了防止下游 `respond` 再读到 `undefined`；实体选择检查是为了防止把虚拟/空结果当成功。实际项目应按该版本 `get.itemtype` 与返回对象约定微调，但原则是“先验证，再调用 `player.respond`”。

若优先级是绝对消除空响应崩溃而不是保持“有实体杀不得取消”，可将该次选择始终设为 `forced:false`，并统一以后置验证；代价是有实体杀时角色可以主动取消，规则语义变弱。因此推荐前一种补强，而不是单纯放弃 forced。
