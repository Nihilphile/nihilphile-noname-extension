# 协攻：杀参数与响应链调查

## 结论

目标版本可以直接表达该规则，推荐组合如下：

1. 【协攻】使用 `trigger: { global: "useCard1" }`，过滤 `event.card.name === "sha"` 且 `event.player` 是当前“帅”。技能本身为锁定触发（`forced: true`）；每名存活的【协攻】拥有者各触发一次。
2. 先用 `player.hasUsableCard("sha", "respond")` 做合法响应能力门：为假时不创建选择事件，直接把“无合法【杀】”交给上层失败分支；为真时使用 `await player.chooseToRespond(...).set("forced", true).forResult()`。`forced` 会移除取消入口：有多张合法【杀】时仍由该角色选一张，但不能主动拒绝。调用成功会真正创建 `respond` 事件，以 `result?.bool === true` 判成功。
3. 每次成功立刻令顶层 `useCard` 事件的 `baseDamage += 1`，并对 `game.players.concat(game.dead)` 中每名角色的 `trigger.customArgs[playerid].shanRequired` 加一；未初始化时从默认一张【闪】变成两张。
4. 不要只遍历 `trigger.targets`。对所有当前角色预写 `customArgs[playerid]`，可以覆盖稍后由 `useCard1`/`useCard2` 加入的额外目标；逐目标创建 `sha` 事件时，引擎会把顶层 `baseDamage` 和该目标的 `customArgs` 复制进去。
5. 多名拥有者不需要自建并发或队列：引擎按触发调度顺序逐个 `await` 技能事件，因此响应框不会并行。相同优先级下按从当前阶段角色等锚点起算的座次序处理；规则不应依赖某一名协攻者必定先行动。
6. 【杀】在 `useCard1` 之后才被排除、取消或无效时，已经打出的协攻【杀】不返还；加成留在本次 `useCard` 上但没有有效目标便不会产生伤害或出【闪】请求。这符合“帅使用【杀】后”触发，而不是“该【杀】生效后”触发。

这里的“打出【杀】”采用无名杀通常语义：可通过合法的转化技打出一张名称为【杀】的响应牌，`result.cards` 是实际消耗的实体组成牌。若规则另行要求“牌面原名必须是【杀】，禁止转化技”，不能只用 `{ name: "sha" }`，见“未知与版本风险”。

## 事件/API 链

```text
帅 useCard(杀)
  -> 初始化 baseDamage=1、customArgs={default:{}}
  -> 使用杀的实体牌进入处理区
  -> useCard0
  -> useCard1
       -> 协攻者 A 的 global useCard1 触发
            -> hasUsableCard(杀, respond)
            -> false: 直接返回失败，不创建强制选择
            -> true: chooseToRespond(杀, forced=true)
            -> 成功: respond 实体牌 -> 处理区 -> 弃牌堆
                     useCard.baseDamage += 1
                     每个 playerid 的 shanRequired += 1
            -> 失败: { ok:false, reason } 交给上层失败分支
       -> 协攻者 B 的 global useCard1 触发（等待 A 完成后）
            -> 同上；成功则再次累加
  -> yingbian
  -> useCard2（仍可能追加目标）
  -> useCard
  -> 目标分拣
  -> 每个未死亡、未移出、未排除的目标：
       创建 sha 事件
       复制累计后的 baseDamage
       复制 customArgs[target.playerid].shanRequired
       循环请求足量的闪；不足则按累计基础伤害命中
```

## 确认、推断与未知

### 已确认

- `useCard1` 位于使用牌实体移动和用牌日志之后，且早于 `useCard2`、目标分拣和逐目标 `sha` 内容。
- 多个同名全局触发由事件调度器串行 `await`，不会同时弹出响应选择。
- `baseDamage` 是顶层统一值，逐目标复制；`shanRequired` 是按 `playerid` 存储并在逐目标创建事件时复制的值。
- `shanRequired` 的安全累加惯例是“已有数字则 `++`，否则置 2”。
- `hasUsableCard("sha", "respond")` 可作为无合法【杀】的失败门；通过该门后，标准 `chooseToRespond` 配置 `forced: true` 没有主动取消入口。成功会生成 `respond`，实体组成牌进入处理区并在响应结束后弃置。
- 目标被 `excluded` 后不会进入 `sha` 内容，因此不会请求【闪】或造成伤害。

### 有证据的推断

- 对所有现存角色预写 `customArgs[playerid]` 能覆盖之后追加的额外目标。推理桥梁是：可追加目标来自现存角色集合，而逐目标事件最终只按该目标的 `playerid` 取参数。
- 后续全目标取消/排除不应退还协攻牌。推理桥梁是：【协攻】已经在 `useCard1` 独立完成 `respond` 和牌移动；目标排除发生于后续阶段，源码没有回滚先前子事件的机制。
- 多个成功协攻与【无双】等按惯例使用 `++` 的效果可交换次序叠加；最终所需【闪】数为 `1 + 成功协攻数 + 其他加成数`。

### 未知/不在本报告范围

- “实体【杀】”是否排除把其他实体牌转化为【杀】。标准 `{ name: "sha" }` 会接受合法转化响应；若必须限制牌面原名，需要另做严格过滤与禁用响应技能的接口验证。
- 第三方技能若在【协攻】之后直接覆盖而非累加 `baseDamage` 或 `shanRequired`，可能覆盖本效果；本报告只确认目标版本内置惯例。
- 极端情况下在 `useCard1` 内创建/复活一个不在预写集合中的全新角色，需补写其 `customArgs`；常规身份局不会发生。
- 联机同步尚未实机验证；这里使用的均是该版本标准事件与玩家选择接口，没有自定义并行状态。
- 失败后的交牌 API 不属于本报告问题，未调查。

## 最小伪代码

```js
const xiegong = {
  trigger: { global: "useCard1" },
  forced: true,
  filter(useCardEvent, owner) {
    return owner.isIn()
      && useCardEvent.card?.name === "sha"
      && isCurrentCommander(useCardEvent.player);
  },
  async content(event, trigger, owner) {
    const canRespondSha = owner.hasUsableCard("sha", "respond");
    if (!canRespondSha) {
      const outcome = { ok: false, reason: "unavailable", cards: [], card: null };
      event.result = outcome;
      await resolveXiegongFailure(owner, trigger.player, outcome); // 交牌另报调查
      return;
    }

    const choose = owner.chooseToRespond(
      "协攻：请选择并打出一张【杀】",
      { name: "sha" }
    );
    choose.set("forced", true); // 有合法杀时只能选杀确认，界面不提供取消
    const result = await choose.forResult();

    const outcome = {
      ok: result?.bool === true,
      // false 是能力检查与实际选择间状态变化的防御分支，不代表允许拒绝
      reason: result?.bool === true ? "responded" : "became-unavailable",
      cards: result?.cards || [],
      card: result?.card || null,
    };
    event.result = outcome; // 便于单元测试；上层也可直接使用局部 outcome

    if (!outcome.ok) {
      await resolveXiegongFailure(owner, trigger.player, outcome); // 交牌另报调查
      return;
    }

    trigger.baseDamage += 1; // useCard 顶层在此前已经初始化

    const map = trigger.customArgs;
    for (const current of game.players.concat(game.dead)) {
      const id = current.playerid;
      map[id] ??= {};
      if (typeof map[id].shanRequired === "number") {
        map[id].shanRequired += 1;
      } else {
        map[id].shanRequired = 2;
      }
    }
  },
};
```

实现时不要再手工调用 `owner.discard(result.cards)`；成功的 `chooseToRespond` 已完成响应牌移动。若需要让其他技能把这张响应识别为“响应帅的这张【杀】”，应另做 `respondTo` 关联的小范围验证；本规则的数值加成与牌去向不依赖该字段。

## 版本风险

- 本结论锁定 v1.11.3。关键私有/半公开字段是顶层 `useCard.customArgs`、`baseDamage`、`playerid` 键及显式阶段名 `useCard1`；升级版本必须复核 `content.js` 的初始化、阶段顺序和逐目标复制。
- `game.players.concat(game.dead)` 是本版本引擎强化效果自身采用的模式，但它是快照式遍历，不是“未来角色”的动态默认值。
- 不建议把加成只写进 `customArgs.default.shanRequired`：逐目标参数会在默认值之后覆盖同名键，与【无双】等效果的先后顺序更容易产生覆盖，而逐 `playerid` 执行 2/++ 与内置惯例一致。
- `forced` 才负责禁止主动拒绝；`autochoose` 只优化部分配置下的无牌返回，`forceDie` 只负责死亡状态下继续事件。三者不能互换。
- 不可对“可能无牌”的事件只设 `forced: true`：本版本会放宽强制事件的最少选择数检查，可能产生空确认。推荐固定顺序是 `hasUsableCard("sha", "respond")` 为假直接失败，为真才创建强制响应。
- `hasUsableCard` 与实际选择之间理论上仍可能被 `onChooseToRespond` 或第三方动态钩子改变合法性，所以保留 `result?.bool !== true` 的防御失败分支，但 UI/AI 不提供主动拒绝路径。

## 回归用例

### RC-02：单人成功协攻

- 初始：帅对一个目标使用普通【杀】；一名【协攻】拥有者有可响应的【杀】。
- 行为：拥有者打出【杀】。
- 断言：`respond` 发生一次；其实体组成牌最终在弃牌堆；顶层 `baseDamage` 由 1 变 2；目标的 `shanRequired` 为 2。
- 断言：目标只出一张【闪】时仍继续请求；出满两张才抵消，否则受到 2 点基础伤害（再由其他减伤/加伤效果结算）。

### RC-03A：无杀失败

- 初始：【协攻】拥有者 `hasUsableCard("sha", "respond") === false`。
- 断言：不创建 `chooseToRespond` 或 `respond`；规范化结果为 `{ ok:false, reason:"unavailable" }`；不改变 `baseDamage`/`shanRequired`；上层失败分支恰执行一次。

### RC-03B：有多张合法杀时不得拒绝

- 初始：拥有者有两张可响应的【杀】。
- 断言：界面只允许选择其中一张后确认，不出现取消入口；AI 也必须选择合法牌；最终 `result.bool === true`，且只消耗所选一张。

### RC-03C：牌名是杀但当前不可合法响应

- 初始：拥有者有牌名为【杀】的牌，但所有候选均被 `cardRespondable`/临时规则禁用，因此 `hasUsableCard("sha", "respond") === false`。
- 断言：能力门直接进入 `{ ok:false, reason:"unavailable" }`，不弹出无牌的强制选择，不累计参数；上层失败分支恰执行一次。

### RC-04A：多拥有者累计

- 三名【协攻】拥有者依次返回成功、失败、成功。
- 断言：响应请求严格串行；成功响应牌各正常弃置；最终 `baseDamage === 3`，每名潜在目标的 `shanRequired === 3`；失败者不贡献加成。

### RC-04B：多目标与额外目标

- 帅最初指定 A，协攻成功两次；随后在 `useCard1` 或 `useCard2` 把 B 加入目标。
- 断言：A、B 创建的 `sha` 事件都读取 `baseDamage === 3`、`shanRequired === 3`；不能出现 A 得到加成而 B 仍只需一张【闪】。

### RC-04C：部分排除/全部取消

- 协攻完成后把 A 加入 `excluded`，B 保持有效。
- 断言：A 触发 `useCardToExcluded`，不请求【闪】且不受伤；B 仍按累计参数结算；已打出的协攻【杀】不返还。
- 再测 `all_excluded` 或在后续阶段终止整张【杀】：无目标请求【闪】或受到伤害，但成功协攻的响应牌仍在弃牌堆。

### RC-04D：与【无双】组合

- 帅或相关效果令同一目标另有一次所需【闪】数加成，另有两次成功协攻。
- 断言：无论同级技能先后，遵守内置 2/++ 累加的实现最终应需 4 张【闪】，不能由某次赋值覆盖成 2 或 3。
