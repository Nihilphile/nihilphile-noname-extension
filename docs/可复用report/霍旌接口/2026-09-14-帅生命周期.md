# 结论

目标版本里，最小且最稳的“帅”表达不是在每名霍旌的 `storage` 中分别保存一个目标，而是把一个**静态、可转移的标记技能**（下文称 `nihil_huojing_shuai_mark`）挂在当前帅本人身上：

- 权威查询：`game.players.find(p => p.hasSkill("nihil_huojing_shuai_mark"))`。
- 公开显示：标记技能声明 `charlotte: true`、`mark: true`、`marktext: "帅"` 和 `intro`。
- 唯一迁移：所有入口只调用同一个 `setCommander(target)`；它先从 `game.players.concat(game.dead)` 清除所有旧 `nihil_huojing_shuai_mark`，再给目标添加一次。
- 死亡继任：把 `player: "dieAfter"`、`forceDie: true` 的继任逻辑直接放在标记技能上。这样触发者就是唯一的旧帅，不需要每个霍旌都监听并争抢继任。
- 遗忠授技：用霍旌自身的 `player: "die"`、`forceDie: true` 可选触发；只允许选择存活且尚无【协攻】的目标，然后 `await target.addSkills("nihil_huojing_xiegong")`。

此模型把“谁是帅”变成目标角色的单一事实，避免多霍旌各自保存不同目标、旧引用未清理、死亡后 owner-storage 悬空等分叉。

联机中的**在场客户端同步**有源码闭环：`addSkill/removeSkill` 会广播技能数组变化，`markSkill/unmarkSkill` 会广播标记 UI。断线重连则存在 v1.11.3 的引擎级缺口：`arenaState()` 的角色快照不含运行时技能或 `storage`，`reinit` 入参也未显式携带 `get.skillState()`；因此不能仅凭这些源码承诺“重连瞬间一定恢复标记”。实现应保留静态标记技能作为服务端权威，在阶段边界主动 `syncSkills()` 并再次 `markSkill()` 自愈，同时把“断线后立即可见”和“下一个事件后可见”列为实机联机回归项，未实测前不得宣称完全通过。

# 范围与停止条件

调查只覆盖：

1. 开局/进入游戏初始化、霍旌准备阶段迁移和全场唯一性；
2. 帅死亡后的继任、霍旌死亡时的【协攻】授技；
3. 进入游戏、在场联机同步、断线重连、死亡顺序、重复技能和多霍旌边界。

未调查【协攻】的响应/伤害/闪数实现，也未读取禁止文件。证据已经由两类来源相互印证后停止：

- 角色包里的相邻正式实现：关系标记、进入游戏兼容、死亡时选择并授技；
- 引擎实现：标记/技能广播、技能幂等、死亡事件顺序、状态序列化与重连路径。

# 文件与行号证据

## A. 相邻正式技能

### A1. `dcfudao`：开局与进入游戏、关系标记

`character/xianding/skill.js:34168-34193`

- 同时监听 `global: "phaseBefore"` 和 `player: "enterGame"`；

### A2. `dushi`：死亡时选择存活目标并授予技能

`character/xianding/skill.js:39512-39539`

- 监听 `player: "die"`，声明 `forceDie: true`；
- 用 `game.hasPlayer(current => current != player)` 判断仍有候选人；

这与【遗忠】的事件形态完全对应。霍旌版只需增加 `target.isIn()` 和 `!target.hasSkill("nihil_huojing_xiegong")`，并保持“可”而非强制选择。

## B. 引擎接口

### B1. 技能和标记的实时广播

`noname/library/element/player.js:10571-10640`

- `addSkill` 在技能已存在时直接返回（10578-10580），底层具备幂等性；
- 新增技能时更新 `player.skills` 并用 `game.broadcast` 同步远端（10586-10595）；
- 若技能声明 `mark`，随后调用 `markSkill`（10606-10633）。

`noname/library/element/player.js:9844-9905`

- `markSkill` 同时写录像事件，创建/更新本地标记，并通过 `game.broadcast` 把 storage、玩家、技能名和标记信息发给其他客户端（9844-9882）；
- `unmarkSkill` 同样写录像并广播删除标记（9885-9905）。

`noname/library/element/player.js:11099-11130`

- `removeSkill` 先 `unmarkSkill`，再用 `game.broadcastAll` 从技能、隐藏技能、临时技能和 additionalSkills 中清理该技能。

所以 `setCommander` 通过“旧帅 `removeSkill` → 新帅 `addSkill`”即可覆盖当前牌局的服务端状态、在场客户端技能状态和公开标记，不要另写只改 DOM 的徽标。

### B2. `addSkills` 的事件语义与重复技能

`noname/library/element/player.js:10545-10569` 与 `noname/library/element/content.js:381-424`

- `addSkills` 创建 `changeSkills` 事件；
- 事件会去重传入数组，触发 `changeSkillsBefore/Begin/End/After`，再调用底层 `player.addSkill`；
- 底层 `addSkill` 对已有技能无操作，但 `changeSkills` 本身未先从 `addSkill` 列表中过滤“已经拥有”的技能，仍可能产生“获得技能”的日志。

因此【遗忠】目标过滤必须显式排除已有【协攻】者，既保持规则的“不重复”，也避免误导日志。

### B3. 死亡顺序

`noname/library/element/content.js:11713-11780`

- `die` 内容一开始令事件 `forceDie = true`；
- 角色在 11744-11758 已从 `game.players` 移入 `game.dead`；
- 之后才在 11778-11780 触发技能时机 `die`。

`noname/library/element/content.js:11782-11824`

- `die` 触发完成后，引擎清除死亡角色的公开 mark UI；
- 这里只调用 `unmarkSkill(mark)`，不是移除全部常驻技能；随后只清理临时技能。

这给出两个实现约束：

1. 【遗忠】在 `player: "die"` 触发时，候选人应从 `game.players` 取，因为死者已经不在其中；死亡角色发起选择必须保留 `forceDie`。
2. 帅的继任用标记技能自己的 `player: "dieAfter"`，并声明 `forceDie: true`。即使引擎先清掉旧帅标记 UI，常驻标记技能仍能完成“清旧技能、给继任者加技能”，新帅会重新生成公开标记。

### B4. 联机序列化与重连风险

`noname/get/index.js:1843-1863`

- `get.skillState()` 明确收集每名在线角色的 `skills`、`hiddenSkills`、`additionalSkills`、`disabledSkills`、`tempSkills` 和 `storage`。

`noname/get/index.js:2662-2767`

- 联机序列化可把 Player 转为 `_noname_player:<playerid>` 并在接收端还原；普通对象、数组也递归处理。

这说明引擎能同步运行时技能/存储，但霍旌无需把 Player 引用当主状态；“标记技能归谁所有”更简单。

重连的负证据同样明确：

- `noname/get/index.js:1823-1841` 的 `arenaState()` 调用每名角色的 `getState()`；
- `noname/library/element/player.js:4158-4248` 的 `getState()` 包含体力、身份、牌区、存活状态等，但不含运行时 `skills`/`storage`/marks；
- `noname/library/index.js:11734-11743` 服务端发出的 `reinit` 参数是配置、`arenaState()`、模式 `game.getState()` 等，未显式传 `get.skillState()`；
- `noname/library/index.js:12671-12925` 重建角色并启动循环，也未见统一调用 `applySkills(get.skillState(...))`。

因此：在场广播为**确认**；通用重连快照能否通过其他未展开路径恢复 acquired skill/mark，为**未知/版本风险**。不可把实时广播等同于重连保障。

# 事件/API 链

## 初始化与进入游戏

```text
phaseBefore(game.phaseNumber == 0) / enterGame
  -> 找出全部存活的、原生拥有【战帅】的霍旌
  -> 若当前已有唯一活帅：不抢占
  -> 若没有活帅：仅座次排序后的 canonical 霍旌执行
  -> setCommander(canonical 霍旌)
     -> 清除 live + dead 中所有旧帅标记技能
     -> canonical.addSkill(shuai_mark)
     -> addSkill 广播 + markSkill 广播
```

## 准备阶段迁移

```text
霍旌 phaseZhunbeiBegin
  -> 可选择一名存活角色
  -> 目标 != 该霍旌，且目标 != 当前帅（避免“改为原帅”的空操作）
  -> setCommander(target)
```

多霍旌时，每名仍拥有【战帅】的霍旌都可在自己的准备阶段迁移同一个全局“帅”。这是规则文字“你可以”在全场唯一约束下最直接的解释。

## 帅死亡继任

```text
持有 shuai_mark 的角色 dieAfter
  -> forceDie: true
  -> livingHuojings = game.players 中拥有【战帅】者
  -> 按旧帅起点 sortBySeat，选第一个作为 canonical successor
  -> setCommander(successor 或 null)
```

把监听器放在 `shuai_mark` 上后，旧帅唯一，所以继任入口也天然唯一；不需要依赖多个霍旌触发器的先后顺序。

## 霍旌死亡与遗忠

```text
霍旌 player: die
  -> forceDie: true
  -> 若存在 target.isIn() && !target.hasSkill(xiegong)
  -> 可选择一名目标（chooseTarget 事件也 set forceDie）
  -> await target.addSkills(xiegong)
```

若死亡霍旌同时是帅：先在 `die` 时机处理可选授技；整次死亡事件完成后的 `dieAfter` 再由帅标记技能迁移帅。两者职责不冲突。

# 确认、推断、未知

## 已确认

- `phaseBefore + enterGame` 是正式技能用于“开局或进入游戏”的兼容组合。
- `player: "die" + forceDie + chooseTarget.forceDie + addSkills` 是正式的死亡授技形态。
- `addSkill/removeSkill` 与 `markSkill/unmarkSkill` 对当前在线客户端有广播。
- `addSkill` 对已存在技能底层幂等；【遗忠】仍应在目标过滤阶段排除重复。
- `die` 技能触发前，死者已从 `game.players` 移入 `game.dead`。
- 普通死亡会清标记 UI，但不会在该段逻辑中移除所有常驻技能。

## 有源码支持的推断

- 把死亡继任放到帅标记技能本身，比让每个霍旌监听 `dieAfter` 更稳定，因为只会有一个触发拥有者。
- `setCommander` 同时扫描 `game.players.concat(game.dead)` 可清除因早期 bug、死亡或多霍旌竞争留下的旧标记技能，并恢复唯一性。
- 多霍旌初始化与继任必须人为指定 canonical 顺序；“全场唯一”与“每名霍旌开局都为帅/帅死都成为帅”在多人同将时无法同时逐字满足。

## 未知

- v1.11.3 是否在本报告未展开的网络层另行补发录像/技能状态，使重连客户端立即重建 acquired mark skill。
- `dieAfter` 上由死亡角色所持的 `forceDie` 标记技能，在所有扩展/联机组合下是否均稳定触发；相邻实现和引擎语义支持此方案，但仍需目标包实测。
- “中途加入角色”具体由哪些模式实际触发 `enterGame`；接口存在，模式覆盖仍需运行验证。

# 最小伪代码

```js
const ZHANSHUAI = "nihil_huojing_zhanshuai";
const SHUAI = "nihil_huojing_shuai_mark";
const XIEGONG = "nihil_huojing_xiegong";

function allPlayers() {
  return game.players.concat(game.dead);
}

function getCommander() {
  return game.players.find(p => p.hasSkill(SHUAI));
}

function livingHuojings(start) {
  return game.players
    .slice()
    .sortBySeat(start || game.players[0])
    .filter(p => p.hasSkill(ZHANSHUAI));
}

function setCommander(target) {
  // 唯一规范化入口；不要在其他位置直接写 storage/mark。
  for (const current of allPlayers()) {
    if (current !== target && current.hasSkill(SHUAI)) {
      current.removeSkill(SHUAI);
    }
  }
  if (target?.isIn() && !target.hasSkill(SHUAI)) {
    target.addSkill(SHUAI);
  }
  // 当前在线客户端的显式修复；对重连仍需实机验收。
  if (target?.isIn()) {
    target.syncSkills();
    target.markSkill(SHUAI);
  }
}

skills[SHUAI] = {
  charlotte: true,
  mark: true,
  marktext: "帅",
  intro: { name: "帅", content: "当前的“帅”" },
  trigger: { player: "dieAfter" },
  forced: true,
  forceDie: true,
  group: SHUAI + "_repair",
  async content(event, trigger, player) {
    const successor = livingHuojings(player)[0] || null;
    setCommander(successor);
  },
  subSkill: {
    repair: {
      // 重连客户端的最终可见性仍需实测；此处在每个回合边界强制补发。
      trigger: { global: "phaseBefore" },
      forced: true,
      silent: true,
      popup: false,
      content(event, trigger, player) {
        const holders = game.players
          .slice()
          .sortBySeat()
          .filter(p => p.hasSkill(SHUAI));
        if (holders[0] !== player) return player.removeSkill(SHUAI);
        player.syncSkills();
        player.markSkill(SHUAI);
      },
    },
  },
};

skills[ZHANSHUAI] = {
  group: ["..._init", "..._change"],
  subSkill: {
    init: {
      trigger: { global: "phaseBefore", player: "enterGame" },
      forced: true,
      silent: true,
      filter(event, player) {
        if (event.name === "phase" && game.phaseNumber !== 0) return false;
        if (getCommander()) return false;
        return livingHuojings()[0] === player;
      },
      content(event, trigger, player) {
        setCommander(player);
      },
    },
    change: {
      trigger: { player: "phaseZhunbeiBegin" },
      direct: true,
      async content(event, trigger, player) {
        const old = getCommander();
        const result = await player.chooseTarget(
          "是否更改“帅”？",
          (card, owner, target) => target.isIn() && target !== owner && target !== old
        ).forResult();
        if (result.bool) setCommander(result.targets[0]);
      },
    },
  },
};

skills.nihil_huojing_yizhong = {
  trigger: { player: "die" },
  direct: true,
  forceDie: true,
  filter(event, player) {
    return game.hasPlayer(target =>
      target !== player && target.isIn() && !target.hasSkill(XIEGONG)
    );
  },
  async content(event, trigger, player) {
    const result = await player.chooseTarget(
      "是否令一名角色获得【协攻】？",
      (card, owner, target) =>
        target !== owner && target.isIn() && !target.hasSkill(XIEGONG)
    ).set("forceDie", true).forResult();
    if (result.bool) await result.targets[0].addSkills(XIEGONG);
  },
};
```

伪代码中的 `sortBySeat` 起点和技能 ID 应按最终模块命名调整。若开发者希望“遗忠可选自己”，该规则在 `die` 时机无法成立，因为死者已不在 `game.players` 且不是存活目标；本需求原文“一名角色”结合死亡场景，建议明确为一名其他存活角色。

# 多霍旌与多名继承者策略

## 多霍旌

- 开局：座次顺序第一名霍旌初始化为帅；其他初始化触发看到已有帅即退出。
- 迁移：每名霍旌只在自己的准备阶段拥有一次可选迁移权。
- 帅死亡：按“从旧帅开始的座次顺序”选第一名存活霍旌继任。
- 若没有存活霍旌：清除旧帅技能，场上暂时无帅；不能让死者继任。
- 后续若新霍旌通过 `enterGame` 入场且场上无帅：其成为帅；若已有帅则不抢占。

这套策略是确定性的，但属于为解决规则文字冲突而增加的实现约定，应在用例/注释中固定。

## 多名遗忠继承者

- 每名霍旌死亡时可以各授予一名不同角色【协攻】；【协攻】不是唯一技能。
- 已有【协攻】者不得再次成为目标。
- 后续协攻触发若需要排序，应另按座次逐名结算；不应把“协攻是否唯一”混入帅身份状态。

# 版本风险

1. **重连高风险**：通用 `reinit` 快照未显式包含运行时技能/存储/marks。实现后的单机和在场联机成功不能替代断线重连验收。
2. **标记死亡可见性**：引擎在 `die` 后会统一清除死者 mark UI。继任必须重新给新帅 `addSkill/markSkill`，不能只移动 storage 引用。
3. **多霍旌规则缺省**：原文没有规定多人同将的初始化/继任优先级。必须使用确定性座次规则，否则结果会依赖触发排列。
4. **重复授技日志**：底层技能添加幂等，但 `addSkills` 事件仍可能记录“获得技能”；在目标过滤处排除已有者。
5. **外部移除技能**：若别的效果能移除 `nihil_huojing_shuai_mark`，可能造成无帅。将其设为 `charlotte` 并让阶段边界规范化；是否需 `fixed` 取决于包内对不可移除技能的约定，不能仅为防御性目的贸然设置。
6. **死者技能触发**：标记技能必须声明 `forceDie: true`。联机/特殊死亡（休整、移出游戏、替换角色）需另测，不能由普通 `die` 推及。

# 回归用例

## RC-01 帅初始化、迁移、唯一性

1. 单霍旌正常开局：开局只有霍旌拥有“帅”公开标记。
2. 霍旌 `enterGame` 且场上无帅：立即成为帅。
3. 霍旌 `enterGame` 且已有帅：不抢占。
4. 霍旌准备阶段取消：帅不变。
5. 霍旌准备阶段选择非自己、非旧帅角色：旧帅标记消失，新帅标记出现；全场技能持有者计数恒为 1。
6. 多霍旌开局：仅座次 canonical 霍旌成为帅，结果不依赖触发弹窗顺序。
7. 人工注入两个帅标记后调用任一迁移/规范化入口：恢复为恰好一个。

## RC-06 死亡继任、授技

1. 非霍旌帅死亡，场上一个存活霍旌：`dieAfter` 后霍旌成为帅。
2. 霍旌本人是帅并死亡，且无其他霍旌：旧标记清除，场上无帅。
3. 霍旌本人是帅并死亡，且另有霍旌：按旧帅起点座次的第一名存活霍旌继任。
4. 霍旌死亡时取消【遗忠】：无人新增【协攻】。
5. 霍旌死亡时选择无【协攻】的存活目标：目标获得技能，当前在线各端均可见。
6. 全部存活角色已有【协攻】：不弹无效选择，也不产生重复获得日志。
7. 多名霍旌先后死亡：可以产生多名不同【协攻】继承者；同一目标不能重复授技。
8. 霍旌同时为帅且死亡：遗忠选择完成一次，随后帅继任完成一次；无重复弹窗、无两个帅。

## RC-07 生命周期与联机

1. 单机开始、迁移、死亡、继任后，检查 `game.players.concat(game.dead).filter(has SHUAI)` 的数量及归属。
2. 两个在场联机客户端观察初始化/迁移/继任：技能效果与“帅”标记同步出现/移除。
3. 迁移前断线、迁移后重连：重连瞬间检查“帅”标记；再推进一个阶段边界复查。
4. 【遗忠】授技后目标断线重连：重连后检查 `hasSkill(XIEGONG)` 与实际触发能力。
5. 帅死亡处理过程中断线重连：不得恢复旧帅、产生双帅或丢失继任者。
6. 录像回放：迁移和继任前后标记 UI 与权威技能持有者一致。
7. 特殊模式的 `enterGame`、休整/复活、角色替换：分别记录是否走普通 `die/dieAfter`；不走者需要单独生命周期适配。

# 验收界线

- RC-01 与 RC-06 可以通过单机自动化/脚本化状态断言覆盖核心逻辑。
- RC-07 的当前在线广播可由双客户端验证；断线重连必须有真实客户端证据。
- 在真实重连证据完成前，结论只能是“服务端单一事实 + 当前在线同步已设计，重连待验”，不能标成完整联机通过。
