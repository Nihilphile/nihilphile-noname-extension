# 无名杀可复用报告治理契约

本目录保存两类材料：带具体任务语境的原始调查档案，以及从证据中晋升出的武将无关机制文档。目标是让后续创作或调试快速找到适用结论，同时保留完整来源和不确定性。

## 文档层次

### 原始调查档案

- 可以按武将、任务或故障命名，保留问题、目标版本、实际读取范围、源码锚点、测试结果和未知项。
- 是机制页的证据来源，不自动成为跨版本接口保证。
- 调查未完成时使用 `located`、`partial` 或 `blocked` 等状态，并具体说明缺口。
- 默认保留原位；晋升不删除原报告。

### 可复用机制文档

- 按事件、响应、牌移动、生命周期、AI 等机制命名，正文结论不依赖特定武将才能成立。
- 可以引用武将案例，但必须把案例特例与通用机制分开。
- 优先修订已有权威页面；只有语义和证据边界确实独立时才新建入口。
- 每个专题目录用 `README.md` 维护快速入口、关键词、证据状态和档案来源。

现有目录不因本契约自动迁移。新增或本次修改的文档遵守本契约；历史文档按实际任务逐步整理。

## 证据状态

机制页至少声明目标游戏版本、最后复核日期和以下三个维度；每个维度可为 `true`、`partial` 或 `false`，并在正文解释 `partial` 的具体覆盖范围。

- `source-confirmed`：主张由目标版本的真实源码及调用上下文直接支持。
- `automated-tested`：主张由实际运行的自动化测试支持，而不是文本搜索或未执行的测试代码。
- `game-confirmed`：主张已在声明版本和环境的真实游戏流程中观察；单机、联机和重连分别记录。

状态彼此不能替代。源码确认不代表实机可用，部分 smoke test 不代表通用模式全部通过，用户一次成功也不外推到其他版本。

推荐的新机制页头部：

```yaml
---
title: 机制名称
game_version: "明确版本或构建标识"
evidence_status:
  source-confirmed: true
  automated-tested: partial
  game-confirmed: false
last_reviewed: YYYY-MM-DD
keywords: [eventName, apiName]
---
```

## 晋升门

一条原始结论只有同时满足以下条件才进入机制页：

1. 能脱离当前武将表述为可复用的事件、API、时序或失败边界。
2. 目标版本和实际调查范围明确。
3. 关键主张能追到真实存在的源码、测试或实机证据；引用包含足以重新定位的路径、符号和行号范围。
4. 已检查同义机制页和相反结论。
5. 已区分确认事实、证据支持的推断、未知项和版本风险。
6. 自动化及实机状态只声明真实覆盖范围。

不满足晋升门的内容继续留在原始档案。没有新通用知识时记录“无需晋升”，不创建空白页面。

## 冲突处理

- 日期较新或报告数量较多都不能单独胜出；优先采用更直接、调用链更完整、目标版本更匹配的证据。
- 保留发生冲突的原始档案；在权威机制页和索引中说明被降级结论、降级原因及当前推荐边界。
- 调用时序必须逐步闭合。发生在 `await`/`forResult()` 返回前的内部效果或异常，不能声称由返回后的校验预防。
- 无法判定时并列记录竞争解释和所需验证，不编造统一答案。

## 来源与链接

- 机制页设置“来源 / 案例”段落，使用相对链接指向原始报告；原始报告可反链当前机制入口。
- 专题索引指向当前权威机制页，并把任务/武将报告明确标作“原始档案”或“案例”。
- 移动或改名历史文件前先检查所有入链；普通晋升不移动原始档案。
- 文件名中的括号和非 ASCII 字符属于合法路径；链接检查必须按 Markdown 目标解析，不能用遇到第一个右括号或右圆括号即停止的简单正则作唯一证据。

## 写入与核验边界

执行知识晋升的代理只写本报告根目录。为了核验，它可以只读：规则契约、原始调查、报告引用的精确源码上下文、最终实现、相关测试和真实运行结果；不能顺带修改实现、测试、游戏源码或交付包。

写入完成后由主控复读关键结论、证据状态、冲突说明和变更链接。报告代理的结论不是权威，能够复查的证据链才是权威。
