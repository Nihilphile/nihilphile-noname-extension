## 0. 结论速览

1. 正常伤害的关键顺序是：`changeHp` 实际扣血 → 内部 `damage` 节点 → 必要时完整等待 `dying` 救援或死亡 → `damageSource` → 事件循环自动产生 `damageEnd` → `damageAfter`。因此“受到伤害后，并且受伤者仍存活在场”适合监听 `global: "damageEnd"`，再过滤 `event.num > 0`、`!event._cancelled` 和 `event.player.isIn()`（`noname/library/element/content.js:11406-11451,11509-11517`；`noname/library/element/gameEvent.js:243-254`；当前实现 `nihilphile武将包/module/luofei.js:621-631`）。
2. 不能笼统地说“`cancel()` 后一定会”或“一定不会”进入 End/After。默认 `trigger.cancel()` 会把 `_triggered` 置为 5，通常直接结束；但如果调用方式没有推进 `_triggered`（例如内容阶段调用 `cancel(false, player)`），`finished` 事件仍可能由循环从状态 2 继续走 End/After。因此后置技能保留 `!event._cancelled` 是有价值的防御性过滤（`noname/library/element/gameEvent.js:597-634,243-254`）。
3. “流失体力”“受到伤害”“体力损失”必须分开建模。落绯采用两个独立的 `changeHpAfter` 子技能：`global` 子技能只认直接父事件为 `loseHp` 的负变化；`player` 子技能认落绯本人所有实际负变化，形成 0/1/1/2 计数。游戏开始时【敛息】另给予2枚初始“血”；伤害转换处不直接产血（当前实现 `nihilphile武将包/module/luofei.js:19-30,346-450`）。
4. `getParent("loseHp")` 未命中时默认返回 `{}`，不是 `null`；所以 `!!event.getParent("loseHp")` 是错误判断。若要认定直接来源，推荐 `event.getParent(1, true)?.name === "loseHp"`；第二参数 `true` 才会让未命中返回 `undefined`（`noname/library/element/gameEvent.js:124-147`）。这次复核已据此修正实现和测试（当前实现 `nihilphile武将包/module/luofei.js:19-30`；测试 `tests/luofei_smoke.js:253-285`）。
5. “翻牌并按颜色分流”的稳定管线是：`get.cards` 取牌 → `cardsGotoOrdering` 放处理区 → `showCards` 展示 → 黑牌 `gain` → 红色实体牌用 `autoViewAs` 包成【杀】 → `hasUseTarget` 预检 → `chooseUseTarget(..., false)` 可选使用且不计次数 → 无目标、主动放弃或异常失败时 `cardsDiscard` → 最后清理仍留在处理区的牌（当前实现 `nihilphile武将包/module/luofei.js:521-611`）。
6. 游戏内导入扩展时，导入器只用精确键 `zip.file("info.json")` 和 `zip.file("extension.js")` 识别扩展；所以二者必须位于 ZIP 根部，不能再套一层同名目录。识别后，ZIP 中每个条目才会被写到 `extension/<扩展名>/<相对路径>`（`noname/game/index.js:2950-2992,3004-3019`）。

## 2. damage、dying 与“受到伤害后”

### 2.1 标准事件循环先产生 Before/Begin，结束后产生 End/After

每个事件进入 `loop()` 后，未完成时依次触发 `<name>Before`、`<name>Begin`，再执行事件内容；内容结束并标为 `finished` 后，状态 2 触发 `<name>End`，状态 3 再触发 `<name>After`（`noname/library/element/gameEvent.js:212-257`）。

对 `damage` 来说，内容本身还会依次触发四个伤害修正节点：`damageBegin1`、`damageBegin2`、`damageBegin3`、`damageBegin4`（`noname/library/element/content.js:11328-11350`）。

### 2.2 实际伤害链

把动画和统计代码略去，真实控制流可以压缩为：

```text
damageBefore → damageBegin
  → damageBegin1 → damageBegin2 → damageBegin3 → damageBegin4
  → changeHp(-num)                 // 实际扣除 HP；护甲在 changeHp 内修正
  → damage                         // num==0 时对应 damageZero
  → 若 hp<=0：等待完整 dying
       → _save 轮询救援
       → 获救，或 die 完成死亡
  → damageSource
  → damageEnd
  → damageAfter
```

证据链如下：

- `damage` 内容先创建 `changeHp(-num, false)`，之后才显式触发 `damage`/`damageZero`（`noname/library/element/content.js:11406-11442`）。
- `changeHp` 会先按伤害父事件和护甲修正 `event.num`，再修改 `player.hp`，最后触发自身的 `changeHp`；其自动 After 节点即技能常监听的 `changeHpAfter`（`noname/library/element/content.js:11599-11635`；通用 After 机制见 `noname/library/element/gameEvent.js:243-254`）。
- 如果扣血后 `hp <= 0`，伤害内容创建 `player.dying(event)`，并用 `return next.forResult()` 等待该子事件完成（`noname/library/element/content.js:11445-11511`）。
- `dying` 先登记濒死并触发 `dying`，随后创建 `_save` 等待救援；仍未回正才 `await player.die(...)`（`noname/library/element/content.js:11658-11710`）。
- 只有上述濒死/死亡处理返回后，damage 的最后一步才触发 `damageSource`（`noname/library/element/content.js:11513-11517`），随后通用循环触发 `damageEnd` 和 `damageAfter`（`noname/library/element/gameEvent.js:243-254`）。

所以玩家对节点顺序的直觉是对的：濒死是插在“受到伤害”与“受到伤害后”之间结算。但“死亡后不会产生 damageEnd”并不成立；外层 damage 仍会完成，只是死亡角色此时已经不在场。

`player.isIn()` 同时排除 dead、out 和 removed（`noname/library/element/player.js:12353-12355`）。因此：

| 伤害结果 | 到 `damageEnd` 时 `event.player.isIn()` | 【流生】是否进入候选 |
|---|---:|---:|
| 未进濒死 | true | 是 |
| 进濒死后获救 | true | 是 |
| 进濒死后死亡 | false | 否 |
| 已离场/被移除 | false | 否 |

官方技能也常用 `damageEnd` 表达“受到伤害后”，例如 `olsishe` 监听 `player: "damageEnd"` 并在内容中读取 `trigger.source`、`trigger.num`（`character/collab.js:5190-5199`）。

### 2.3 为什么过滤 `num > 0`、`!_cancelled`、`isIn()`

推荐骨架：

```js
trigger: { global: "damageEnd" },
filter(event, player) {
    return event.player
        && event.num > 0
        && !event._cancelled
        && event.player.isIn()
        && player.countMark(BLOOD_MARK) > 0;
}
```

- `event.num > 0`：伤害内容在 `num == 0` 时触发 `damageZero`，但未取消的外层事件仍能走到 End/After；后置技能不能只凭事件名认定真的造成了正数伤害（`noname/library/element/content.js:11436-11442`）。
- `!event._cancelled`：`cancel()` 在通常情况下会写入 `_cancelled = true`（`noname/library/element/gameEvent.js:623-633`）。这是对非标准取消路径和其他扩展改写的防御性屏障。
- `event.player.isIn()`：濒死/死亡已在 `damageEnd` 前结算；它精确表达“救回后可以触发，死亡或离场后不触发”（`noname/library/element/content.js:11445-11517`；`noname/library/element/player.js:12353-12355`）。

当前【流生】正是这组过滤（`nihilphile武将包/module/luofei.js:621-631`），相应烟雾测试覆盖了在场、死亡离场和 `_cancelled` 三种输入（`tests/luofei_smoke.js:520-540`）。

### 2.4 取消伤害到底会不会走 End/After

这是最容易被旧经验误导的一点。源码给出的精确答案是“取决于取消方式和当时的 `_triggered` 状态”：

1. 默认 `trigger.cancel()` 调用 `untrigger()`；`untrigger` 的默认 `all = true` 会把 `_triggered` 设为 5，随后 `finish()`（`noname/library/element/gameEvent.js:597-633`）。循环的 finished 分支只为状态 1、2、3安排 Omitted、End、After；状态 5 没有这些分支，通常直接结束（`noname/library/element/gameEvent.js:243-254`）。因此落绯在 `damageBefore` 中执行的标准 `trigger.cancel()` 不会再触发该次伤害的 `damageEnd`（当前转换代码见 `nihilphile武将包/module/luofei.js:403-419`）。
2. 如果调用 `cancel(false, player)` 或其他方式使 `untrigger` 没有把 `_triggered` 置 5，那么 `cancel` 仍会 `finish()`；当事件已处于内容状态 2 时，循环就仍可能接着触发 End 和 After（`noname/library/element/gameEvent.js:597-608,619-634,243-254`）。
3. 如果第三参数 `notrigger` 为 true，`cancel` 甚至不会写 `_cancelled`（`noname/library/element/gameEvent.js:626-633`）。所以 `!_cancelled` 是实用防线，但不是对任意恶意/非标准改写的数学证明。

结论：标准技能一般使用默认 `trigger.cancel()`；后置技能仍应组合 `num > 0`、`!_cancelled`、存活/在场状态与自身业务条件，不要仅依赖“理论上 cancel 后没有 End”。

## 3. 用 changeHpAfter 区分 loseHp 与 damage

### 3.1 术语和真值表

- **流失体力**：特指 `player.loseHp(num)` 创建的 `loseHp` 事件（`noname/library/element/player.js:8504-8521`）。
- **受到伤害**：特指 `damage` 事件；其中会创建 `changeHp(-num)`，并可能先由护甲吸收（`noname/library/element/content.js:11328-11442,11599-11608`）。
- **体力损失**：规则文字层面的上位概念，表示 HP 实际减少；来源既可能是 damage，也可能是 loseHp。

落绯所需计数为：

| HP 下降者 | 直接来源 | 全局“任意角色流失体力” | 自身“你损失体力” | 合计“血” |
|---|---|---:|---:|---:|
| 其他角色 | damage | 0 | 0 | 0 |
| 其他角色 | loseHp | 每点 +1 | 0 | 每点 +1 |
| 落绯 | damage | 0 | 每点 +1 | 每点 +1 |
| 落绯 | loseHp | 每点 +1 | 每点 +1 | 每点 +2 |

这里按 `-changeHpEvent.num` 加标记，而不是按原始 damage/loseHp 的声明值加。`changeHp` 会先处理护甲，再把最终 `event.num` 加到 HP 上（`noname/library/element/content.js:11599-11616`），所以“实际掉几点 HP 就加几点”，护甲完全吸收时不会误加。

### 3.2 两个独立子技能相加

推荐结构：

```js
function isDirectLoseHpChange(event) {
    if (!event || event.num >= 0 || typeof event.getParent !== "function") {
        return false;
    }
    const parent = event.getParent(1, true);
    return !!parent && parent.name === "loseHp";
}

const globalLoseHpCounter = {
    trigger: { global: "changeHpAfter" },
    forced: true,
    filter(event) {
        return isDirectLoseHpChange(event);
    },
    content(event, trigger, player) {
        player.addMark(BLOOD_MARK, -trigger.num, false);
    },
};

const ownerHpLossCounter = {
    trigger: { player: "changeHpAfter" },
    forced: true,
    filter(event) {
        return event.num < 0;
    },
    content(event, trigger, player) {
        player.addMark(BLOOD_MARK, -trigger.num, false);
    },
};
```

`global` 和 `player` 是不同触发角色；事件触发器按 `player/source/target/global` 四种 role 收集技能（`noname/library/element/gameEvent.js:472-475,572-575`）。因此落绯自己 loseHp 时，同一个 `changeHpAfter` 同时满足两个独立子技能，获得两份计数；自己因 damage 掉血时只满足 `player` 子技能。

当前实现对应 `nihil_lianxi_losehp` 和 `nihil_lianxi_selfloss`（`nihilphile武将包/module/luofei.js:422-450`），测试明确锁定完整四格：“其他角色 damage → 0”“其他角色 loseHp 1点 → 1血”“自己 damage 掉1点 → 1血”“自己 loseHp 1点 → 2血”。

【敛息】的伤害转换本身不直接奖励“血”。因此落绯对其他角色造 N 点伤害时，目标改为 loseHp N 点并由全局计数得到 N；若目标恰好是落绯自己，还会命中自身 HP 损失计数，总计 2N（转换测试与四格测试见 `tests/luofei_smoke.js:216-285`）。

### 3.3 `getParent("loseHp")` 的两个边界

`GameEvent.getParent(level, forced, includeSelf)` 支持数字层级、名称或函数；名称形式会沿整个祖先链搜索。默认找不到时返回空对象 `{}`，只有 `forced === true` 才返回 `undefined`（`noname/library/element/gameEvent.js:124-147`）。由此有两个坑：

**坑一：不能直接转布尔值。**

```js
// 错：未找到时 {} 也是真值
!!event.getParent("loseHp")

// 至少要这样
event.getParent("loseHp").name === "loseHp"
// 或
!!event.getParent("loseHp", true)
```

**坑二：名称搜索可能过宽。** `getParent("loseHp", true)` 会查任意深度祖先；若某个 loseHp 结算中嵌套触发了另一条 HP 变化链，深层 changeHp 也可能看到远祖 loseHp。这里要识别的是 `loseHp` 内容直接创建的 changeHp；源码就是 `await player.changeHp(-num)`（`noname/library/element/content.js:11547-11567`），而子事件进入父事件的 `next` 队列时会被赋予该父事件（`noname/library/element/gameEvent.js:149-165`），所以检查直接父事件最稳妥：

```js
event.getParent(1, true)?.name === "loseHp"
```

本次复核曾发现实现使用了错误的布尔判断；现已改为直接父事件 + `forced=true`，测试也特意模拟“默认未命中返回 `{}`、forced 未命中返回 `undefined`”的真实语义，防止回归（`nihilphile武将包/module/luofei.js:19-30`；`tests/luofei_smoke.js:253-285`）。

## 4. 从牌堆顶到实体【杀】：完整牌区管线

### 4.1 为什么要先进入处理区

`get.cards(num)` 会直接从牌堆顶移除指定数量的牌，设置其原始位置为牌堆并返回数组；牌堆空时还会洗牌（`noname/get/index.js:3327-3363`）。取出后应立刻 `await game.cardsGotoOrdering(cards)`：该 API 创建移入处理区的事件（`noname/game/index.js:1328-1341`），其内容把卡牌 append 到 `ui.ordering`，登记移动历史，并给父事件安排 `orderingDiscard` 收尾（`noname/library/element/content.js:2517-2521,2523-2570`）。

这一步带来三点好处：

1. 牌的公开位置明确，后续展示、获得、使用都有可追踪的移动来源。
2. 黑牌 `gain`、红牌作为实体子牌使用时，都从同一个中间区离开，不会出现“牌仍在牌堆但又被使用”的重复归属。
3. 引擎自带 `orderingDiscard` 会在父事件收尾时丢弃仍位于 `o` 的牌（`noname/library/element/content.js:2517-2521,2553-2568`）；技能再做一次显式位置检查，可以更早处理无目标牌，并为中途离场、未知颜色和异常返回提供局部兜底。

`showCards` 只创建展示事件并保存待展示牌数组，本身不是牌区移动 API（`noname/library/element/player.js:6810-6840`）。因此正确顺序是“先入处理区，再展示”，而不是把 `showCards` 当作放置动作。

### 4.2 颜色分流与实体 viewAs

推荐骨架：

```js
const cards = get.cards(num);
await game.cardsGotoOrdering(cards);
await player.showCards(cards, "发动技能");

const blackCards = cards.filter(card => get.color(card, false) === "black");
const redCards = cards.filter(card => get.color(card, false) === "red");

if (blackCards.length) {
    await player.gain(blackCards, "gain2");
}

for (const card of redCards) {
    if (!player.isIn()) break;

    const sha = get.autoViewAs({ name: "sha" }, [card]);

    // true/省略：正常检查距离；false：不检查使用次数限制
    if (!player.hasUseTarget(sha, true, false)) {
        if (get.position(card, true) === "o") {
            await game.cardsDiscard(card);
        }
        continue;
    }

    const result = await player
        .chooseUseTarget(
            { name: "sha", cards: [card] },
            [card],
            false,  // addCount=false；未传 true，因此玩家可以放弃
        )
        .forResult();

    if (!result?.bool && get.position(card, true) === "o") {
        await game.cardsDiscard(card);
    }
}

const leftovers = cards.filter(card => get.position(card, true) === "o");
if (leftovers.length) {
    await game.cardsDiscard(leftovers);
}
```

这里的关键不是只把牌名改成 `sha`，而是把原红牌作为实体子牌传入。`get.autoViewAs(card, cards)` 会构造带子牌的 `VCard`（`noname/get/index.js:1049-1054`）；`chooseUseTarget` 会解析实体 cards、虚拟 card 和布尔参数：传 `true` 才设置 `forced=true`，传 `false` 设置 `addCount=false`。当前技能只传一个 `false`，因此玩家可以取消，同时不计【杀】次数（`noname/library/element/player.js:6115-6170`）。这样花色、点数、牌移动和“这张实体牌已经用掉”都有明确载体。

### 4.3 `hasUseTarget` 的布尔参数陷阱

`hasUseTarget(card, distance, includecard)` 最终逐个调用 `canUse`。源码规定：

- 第二参数只有严格等于 `false` 时才**忽略距离**；传 `true` 或省略才正常检查距离。
- 第三参数为真时才检查 `cardUsable`（包括【杀】次数），并改用 `targetEnabledx`；为 false 时跳过次数限制（`noname/library/element/player.js:10097-10131,10133-10144`）。

因此“正常距离，但不计使用次数”的预检应写：

```js
player.hasUseTarget(sha, true, false)
```

不要凭直觉把第二个 `false` 理解为“不开启距离绕过”。`false` 在这里恰好表示无距离限制。预检与后续 `chooseUseTarget` 的距离规则必须一致，否则可能先判断“有目标”，再弹出一个实际上没有合法目标的选择。无论是否允许主动放弃，都应保留 `forResult().bool` 检查和处理区弃置兜底。

当前【殷潮】在结束阶段可选发动，完成取牌、处理区、展示、黑牌获得、红牌实体化、正常距离预检、逐张可选使用、不计次数、无目标或主动放弃时弃置和最终清理（`nihilphile武将包/module/luofei.js:521-611`）。预检使用 `hasUseTarget(sha, true, false)`；对应测试覆盖取消发动与完整牌区分流（`tests/luofei_smoke.js:287-358`）。

### 4.4 神姜维只是两段相似记忆

“神姜维好像有翻牌后当杀用”的印象来自两个技能的组合，而不是一个完全同构技能：

- 【九伐】取得牌堆顶九张牌，排序并放入处理区，然后让玩家选择满足条件的牌获得；它提供“批量翻顶牌 → 处理区 → 选择并获得”的参考（`character/xianding/skill.js:1448-1513`）。
- 【平襄】循环九次 `chooseUseTarget` 使用虚拟火【杀】，没有使用【九伐】翻出的实体牌；它提供“连续选择【杀】目标”的参考（`character/xianding/skill.js:1596-1625`）。

更接近“处理区实体牌直接使用”的官方片段是【泛音】：牌进入处理区并展示后，以 `get.autoViewAs(card)` 包装，再调用 `chooseUseTarget(cardx, [card], true, false)`（`character/xianding/skill.js:34762-34794`）。【兵临城下】也展示了“牌堆顶牌 → 处理区 → 符合条件的实体【杀】逐张 useCard → 其余牌回牌堆”的完整牌区分流（`character/shiji/card.js:180-206`）。

可复用结论是：不要寻找一个“神姜维同款 API”；应从九伐借牌区流程、从平襄借连续用牌交互、从泛音借实体牌 viewAs，再按本技能的红黑分流规则组合。

## 5. 扩展 ZIP 的游戏内导入契约

### 5.1 入口与识别

扩展菜单只接受 ZIP 文件，读取为 `ArrayBuffer` 后调用 `game.importExtension(...)`（`noname/ui/create/menu/pages/exetensionMenu.js:2291-2298,2314-2338`）。导入函数加载 ZIP 后按以下顺序识别：

```text
zip.file("info.json")
  ├─ 存在：解析 JSON，并临时 import 为 extension 以取得包信息
  └─ 不存在：再尝试 zip.file("extension.js") 并 eval，以取得包信息

仍没有 game.importedPack
  └─ 报错“此压缩包不是一个扩展”
```

对应源码是 `noname/game/index.js:2931-2991`。`game.import` 在 `_status.importingExtension` 期间把扩展对象保存为 `game.importedPack`（`noname/game/index.js:2770-2774`），随后导入器读取其中的 `name` 作为扩展名（`noname/game/index.js:2992-3004`）。

`zip.file("info.json")` 和 `zip.file("extension.js")` 是精确路径查询。因此正确结构必须是：

```text
nihilphile武将包.zip
├─ info.json
├─ extension.js
├─ character/
├─ module/
├─ image/
└─ ...
```

错误结构：

```text
nihilphile武将包.zip
└─ nihilphile武将包/
   ├─ info.json
   └─ extension.js
```

后一种结构中只有 `nihilphile武将包/info.json`，根部查询失败，导入器无法识别扩展。

### 5.2 识别后如何落盘

识别出名称后，导入器：

1. 如同名扩展已存在，先调用移除逻辑；
2. 把名称加入 `lib.config.extensions` 并启用；
3. 以 `extension/<name>` 为目标目录；
4. 遍历 `zip.files`，把每个目录和文件按 ZIP 内相对路径写入目标目录（`noname/game/index.js:2992-3019`）。

当前包的 `info.json` 声明名称为 `Nihilphile`（`nihilphile武将包/info.json:1-9`），`extension.js` 也以 `Nihilphile` 返回扩展对象并登记 `luofei` 模块（`nihilphile武将包/extension.js:1-20,55-66`）。名称一致很重要：落盘目录来自导入阶段识别到的 `game.importedPack.name`，运行时资源路径也以扩展名拼接。

### 5.3 为什么排除嵌套历史 ZIP

导入器只解开最外层 ZIP 一次，并逐条写入 `zip.files`；它不会递归导入其中的 `character.zip`、`info.zip` 等压缩包（`noname/game/index.js:3004-3019`）。把历史 ZIP 一起打进去的后果是：

- 纯粹增加包体和导入时间；
- 在安装目录遗留第二份过期资料，容易让维护者误把它当运行时来源；
- 若历史包结构或内容已过期，会制造“源码目录与内嵌归档不一致”的双重事实源。

因此发布 ZIP 应只包含当前运行时文件，排除旧包、测试、构建缓存和另一个完整扩展目录。需要保留旧版时，应作为外部独立发布物保存，而不是塞进可导入包内部。

### 5.4 当前发布物核验记录

本次对 `nihilphile武将包.zip` 进行了只读复核：共 26 个文件、5 个目录条目，`extension.js` 与 `info.json` 均为根部条目，内嵌 `.zip` 数量为 0；归档内26个文件均与当前源码同名文件逐一通过 SHA-256 内容比对。最终 ZIP 大小为 20,650,198 字节，SHA-256 为：

```text
41757A6CFFC99F371F934CC7D95D5F5018D7831DA914DD5E296A8450051BC58B
```

这项核验确认“本次产物符合当前导入器的结构契约”；契约本身的源码依据仍是根部精确查询与逐条落盘逻辑（`noname/game/index.js:2950-2991,3004-3019`）。以后每次重新打包都应重新统计条目并计算散列，不能沿用本次值。

## 6. 推荐实现骨架

下面是一份可迁移到其他武将的缩略骨架，保留本次最重要的边界：

```js
const MARK = "my_mark";

function isDirectLoseHpChange(event) {
    if (!event || event.num >= 0 || typeof event.getParent !== "function") {
        return false;
    }
    const parent = event.getParent(1, true);
    return !!parent && parent.name === "loseHp";
}

const skills = {
    // 任意角色 loseHp：每实际一点 +1
    count_global_losehp: {
        trigger: { global: "changeHpAfter" },
        forced: true,
        filter: isDirectLoseHpChange,
        content(event, trigger, player) {
            player.addMark(MARK, -trigger.num, false);
        },
    },

    // 技能拥有者一切实际 HP 下降：每点再 +1
    count_owner_hploss: {
        trigger: { player: "changeHpAfter" },
        forced: true,
        filter(event) {
            return event.num < 0;
        },
        content(event, trigger, player) {
            player.addMark(MARK, -trigger.num, false);
        },
    },

    // 受到伤害后且救援完成仍在场
    after_real_damage: {
        trigger: { global: "damageEnd" },
        filter(event, player) {
            return event.player
                && event.num > 0
                && !event._cancelled
                && event.player.isIn()
                && player.countMark(MARK) > 0;
        },
        async content(event, trigger, player) {
            // 消耗标记并执行后续效果
        },
    },

    // 结束阶段可选发动：翻牌并逐张选择是否使用实体牌
    reveal_and_use: {
        trigger: { player: "phaseJieshuBegin" },
        direct: true,
        filter(event, player) {
            return player.countMark(MARK) > 0;
        },
        async content(event, trigger, player) {
            // 先进行可取消的数量选择；取消时不消耗标记、不翻牌。
            const cards = get.cards(/* num */);
            await game.cardsGotoOrdering(cards);
            await player.showCards(cards, "发动技能");

            const gained = cards.filter(card => /* 获得条件 */);
            if (gained.length) await player.gain(gained, "gain2");

            for (const card of cards.filter(card => /* 使用条件 */)) {
                if (!player.isIn()) break;
                const vcard = get.autoViewAs({ name: "sha" }, [card]);
                if (!player.hasUseTarget(vcard, true, false)) {
                    if (get.position(card, true) === "o") {
                        await game.cardsDiscard(card);
                    }
                    continue;
                }
                const result = await player
                    .chooseUseTarget(
                        { name: "sha", cards: [card] },
                        [card],
                        false,
                    )
                    .forResult();
                if (!result?.bool && get.position(card, true) === "o") {
                    await game.cardsDiscard(card);
                }
            }

            const leftovers = cards.filter(card => get.position(card, true) === "o");
            if (leftovers.length) await game.cardsDiscard(leftovers);
        },
    },
};
```

此骨架对应的 API 语义分别由 `getParent`（`noname/library/element/gameEvent.js:124-147`）、`get.cards`（`noname/get/index.js:3327-3363`）、处理区（`noname/game/index.js:1328-1341`；`noname/library/element/content.js:2517-2570`）、`autoViewAs`（`noname/get/index.js:1049-1054`）、`hasUseTarget/canUse`（`noname/library/element/player.js:10097-10144`）和 `chooseUseTarget`（`noname/library/element/player.js:6115-6170`）共同支撑。

## 7. 常见坑检查表

| 坑 | 症状 | 正确做法 | 证据 |
|---|---|---|---|
| 用 `damageEnd` 却不查 `num` | `damageZero` 也进入后置逻辑 | `event.num > 0` | `content.js:11436-11442` |
| 认为濒死晚于 damageEnd | 对死人弹后续交互，或救回者漏触发 | `damageEnd` + `event.player.isIn()` | `content.js:11445-11517` |

## 9. 最小复用原则

如果只带走四条经验，应当是：

1. **后置伤害效果先画出真实事件时间线，再选 damageEnd；死亡过滤不要靠猜，直接查 `isIn()`。**
2. **要区分 damage 与 loseHp，观察最终 `changeHpAfter.num`，再用“直接父事件”标来源。**
3. **牌堆顶实体牌先统一进处理区；每条获得/使用/弃置分支都让牌离开处理区，最后再兜底清场。**
4. **可导入 ZIP 的根就是扩展根；`info.json` 与 `extension.js` 不得藏在外层目录或历史子压缩包中。**

这四条分别解决的是事件语义、数值来源、卡牌所有权和发布边界；它们比复制某个官方技能的整段代码更可复用。

## 10. 终版补充：初始“血”与“生/息”提示

扩展现在只保留角色 `nihil_luofei`，显示名仍为“落绯”。终版新增两项易用性行为：

|---:|---:|---:|---|
| 0 | 无法发动 | 隐藏 | 无 |

【殷潮】则在结束阶段提供一次可取消的发动询问；选择发动后，按1:1移去任意正数枚“血”并翻开等量牌，红牌仍逐张可选是否当【杀】使用（`nihilphile武将包/module/luofei.js:521-611`）。
